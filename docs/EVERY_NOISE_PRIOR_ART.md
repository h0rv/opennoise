# Every Noise prior art audit

Audit date: 2026-08-30

This report reviews open projects and public research related to Every Noise at Once. It focuses on work from 2023 through 2026, with older work where it explains the data or algorithms. The review used repository metadata, source files, project pages, papers, and official data and platform policies. No project was cloned or run. No restricted dataset was downloaded. No endpoint was scraped.

## Decision summary

Musix should reproduce the exploration model, not copy the Spotify corpus.

The useful ideas are a spatial genre browser, a genre and artist graph, active search, explainable similarity, and a clear record of where every fact came from. None of the supplied repositories offers a current, licensed, reproducible copy of the Every Noise system. Most are old scrapers or static snapshots. Several have no license. The largest current corpus found in this review is derived from Spotify data obtained through Anna's Archive. Its availability does not make it licensed or compatible with Spotify policy.

The safe starting point is a Python metadata pipeline built from MusicBrainz core data, Wikidata, and ListenBrainz public listens. SQLite FTS5 supports search. Weighted overlap and cooccurrence can support an initial similarity graph. A deterministic graph layout can support the first map. The first map does not require audio or model training.

The user should stay in charge of later model choices. Good research candidates include
hyperbolic genre embeddings and Word2Vec style cooccurrence over approved metadata. Musix does
not ingest audio or audio-derived feature data.

## What the original project exposed

The final Every Noise map describes 6,291 genre shaped distinctions tracked through 2023-11-19. Glenn McDonald confirmed that final count after losing access to the Spotify data that drove updates. The current public mirror is a static historical artifact, not a live Spotify dataset. Sources: [McDonald interview](https://jbushnell.substack.com/p/wednesday-investigations-211-glenn), [Every Noise public mirror](https://furia.com/everynoise_public/), and [2024 interview](https://www.thirdbridgecreative.com/blog/glenn-mcdonald-q-a).

McDonald's own presentation says the public map is an algorithmically generated and readability adjusted scatter plot. It used ten internal dimensions and two independent measures of genre similarity. The rough visual interpretation was electric toward the top, acoustic toward the bottom, dense toward the left, and sparse or spiky toward the right. The genres overlap and do not form a strict taxonomy. Central genres received more artists than peripheral genres. Source: [How We Understand Music Genres](https://furia.com/everynoise_public/EverynoiseIntro.pdf).

McDonald's 2013 technical notes add two details. The small related genre maps combined direct artist overlap with a separate relation based on audio similarity. The layout then moved labels to make them readable, so it was not a strict plot of raw values. A later note from the same year describes a 12 dimensional analytical space used to find opposite genres from aggregate acoustic properties. This differs from the ten dimensions in the presentation. The system likely changed over time or used different analytical spaces for different views. The public material does not identify a stable feature schema that can be reproduced. Source: [Glenn McDonald's 2013 technical log](https://furia.com/page.cgi?skip=90&tag=tech&type=log).

This sets an important boundary. Public page positions are display coordinates. Color is also a display output. Neither is a disclosed embedding or a reproducible account of the internal analytical space. A scraper can preserve the old picture, but it cannot recreate the original model.

The one dimensional public views add useful product ideas. They sort genres by popularity, emergence, modernity, youth, femininity, engagement, background, tempo, duration, color, name, and date added. They can also sort by similarity to a selected genre. These ranks should be treated as historical Spotify derived outputs, not as fields that Musix can refresh from public Spotify APIs.

### Corrections to the supplied summary

The summary overstates several projects:

1. The 6,044 item Scottsdaaale list is not a comprehensive current Every Noise dataset. The final map had 6,291 genres. The repository has no coordinates or graph.
2. EveryNoise-Watch does not calculate the hidden three dimensional genre space. It extracts x and y page pixels and a rendered RGB color.
3. EveryNoise-Genre-JSON is not a modern platform integration. Its code is a small 2022 HTML splitter against an old CGI page.
4. The quint-t page is not an active reconstruction. It is a static copy with links back to Every Noise.
5. spotify-genre-map stopped its scheduled updates in May 2023 and has no license.
6. every-noise-network-analysis is a 2019 student project, not an active data science library.
7. everynoise_scraper stopped in January 2020, so it is not actively maintained.
8. Music-Marketing is a 2019 marketing experiment, not a newer pipeline package.

### Release, fork, issue, and registry check

Seven of the eight supplied repositories have no GitHub release. EveryNoise-Watch has one release, `v1.0.0` from 2021-05-19, and its open issue asks for a migration from Goodtables to Frictionless. The project networks are small, with zero to five forks each. No fork provides a maintained replacement for the map pipeline.

The only materially renamed recent fork is [hannesdatta/data-spotify-promotions-releases](https://github.com/hannesdatta/data-spotify-promotions-releases), last pushed 2023-01-04. It documents the same two Everynoise scrapers for new releases and world browser playlists and points to [Dataverse DOI 10.34894/0RK0KK](https://doi.org/10.34894/0RK0KK). The repository has no license. Its README still says raw data is confidential and that a public release was expected in 2021, so neither current availability nor reuse rights are clear. It is not an approved Musix input.

A targeted search of PyPI and npm did not find a maintained Every Noise parser or dataset package tied to these projects. The supplied repositories are source snapshots rather than versioned dependencies. Musix implements small typed adapters directly instead of taking an unmaintained package dependency.

## Algorithm findings

The table separates methods that only need metadata from methods that use audio or proprietary derived features.

| Method | Inputs | Output | Audio needed | Evidence and limits |
| --- | --- | --- | --- | --- |
| Weighted Jaccard or cosine overlap | Artist to genre, artist to tag, or playlist cooccurrence edges | Explainable genre and artist similarity | No | A good deterministic baseline. Each score can show the shared evidence. It can be implemented directly in Python. |
| Word2Vec style cooccurrence | Lists of genres on the same artist or item | Dense genre vectors | No | Used by Not Every Noise. It can capture context but does not create a true taxonomy. Results depend heavily on source coverage and negative sampling. Keep it as a user chosen experiment. |
| Hyperbolic cooccurrence embedding | Genre cooccurrence matrix | Lorentz vectors and a Poincare disk view | No direct audio at training time | [Hyperbolic Embeddings for Music Taxonomy](https://aclanthology.org/2020.nlp4musa-1.8/) used 1,368 Every Noise playlists covering 4,309 genre labels. It evaluated 503 normalized matches against FMA, AllMusic, Discogs, Last.fm, and Tagtraum trees. The method is relevant because hyperbolic space can express hierarchy, but the original inputs and several evaluation sources have reuse restrictions. Recreate the experiment only with approved open inputs. |
| PCA plus K means over mean audio features | Spotify track audio features averaged by genre | Low dimensional features and clusters | Yes | Used by every-noise-network-analysis. It asks whether graph communities match acoustic groups. The old Spotify feature endpoint and collected data are not a safe base now. |
| Louvain community detection | Weighted genre similarity graph | Discrete graph communities | No | Useful as an analysis view, not as a single truth about genres. Community resolution and random seeds must be recorded. |
| Force directed, spectral, or multidimensional scaling layout | Weighted graph or distance matrix | Two dimensional display positions | No | Good choices for the first computed map. Fix ordering, seed, parameters, and collision handling for deterministic builds. Layout coordinates should be versioned separately from semantic evidence. |
| Artist barycenter | Weighted artist to genre edges and genre positions | Artist location on the genre map | No | Simple and explainable. Show uncertainty or spread when an artist belongs to distant genres. Do not force one genre label. |
| SQLite FTS5 with aliases | Canonical names, aliases, normalized names, and source IDs | Fast prefix and text search | No | Appropriate for the first product. Ranking can blend exact name, alias, source quality, and graph importance without ML. |
| Embeat dual tower and Track2Vec | Spotify audio features, metadata, related items, and playlist sequences | Track vectors and retrieval candidates | Uses audio features and proprietary derived data | Architecturally interesting, but its source corpus and policy status make it unsuitable for Musix. The user should choose any later model and training data. |

The first map should not label its axes as organic, mechanical, dense, or spiky unless those properties are computed from explicit, reviewable features. A generic graph embedding can resemble the old map while having completely different meaning. An affine fit to old coordinates preserves the old orientation but does not recover the original model.

## Spotify and archive constraints

Spotify cannot be the corpus foundation for this project. Its [Developer Policy](https://developer.spotify.com/policy), effective 2025-05-15, prohibits using Spotify Platform or Spotify Content to train or otherwise ingest into an ML or AI model. It also prohibits broad analysis of Spotify Content and creation of derived metrics. Its terms limit database building and indefinite storage. This affects both fresh API collection and republished Spotify dumps.

Current Development Mode is also too narrow for corpus construction. As of August 2026, an owner needs Premium, an app is limited to five authorized users, and 25 client IDs share one account quota. Spotify removed batch catalog fetches for this mode, reduced search results, removed several browse and artist endpoints and fields, and limits playlist contents to playlists the user owns or collaborates on. Sources: [February 2026 migration guide](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide), [February 2026 change list](https://developer.spotify.com/documentation/web-api/references/changes/february-2026), and [July 2026 quota update](https://developer.spotify.com/blog/2026-07-23-web-api-quota-updates).

Spotify may later be an optional user connected lookup or outbound link if the exact feature complies with current policy, attribution, retention, and quota rules. It should not populate the durable Musix genre graph. The same principle applies to Apple Music. A connector can improve a user's playback flow, but it does not provide a reusable metadata license.

Anna's Archive is a location, not permission. The Embeat project shows that a large Spotify derived collection is circulating there. Musix should not download or ingest it. A claimed CC BY-NC label added by a republisher does not establish authority to relicense Spotify content. Internet Archive access has the same distinction. It can establish what a page looked like at a date, but it does not erase the rights attached to page data, images, or audio.

This is an engineering risk assessment, not legal advice. Any planned release of a copied historical snapshot should receive a specific rights review.

## Ranked Python reuse plan

1. Build the provenance boundary first. Every imported assertion should store source name, source object ID, source URL, snapshot date, content hash, source license, importer version, and confidence. Raw, normalized, and derived records should be separate. A source license must never be inferred from the code license of a scraper.
2. Use MusicBrainz CC0 core records for identity and relationships. Add Wikidata CC0 labels, aliases, and genre hierarchy statements. Preserve conflicting names and relationships rather than overwriting them.
3. Add a metadata only graph in Python. Materialize artist to genre and artist to tag edges in both directions. Build genre cooccurrence counts with minimum support and privacy thresholds. Normalize names for matching, but keep the original text and source ID.
4. Ship deterministic baselines before ML. Use weighted Jaccard or cosine similarity, artist barycenters, SQLite FTS5, and a seeded two dimensional graph layout. Return evidence with every similar genre or artist result.
5. Use the public Every Noise mirror only as a historical benchmark. Keep old positions in a separately named `legacy_display_coordinate` table with capture time and rights status. Never call those values an embedding. Compare coverage and neighborhoods without copying audio or treating the map as current truth.
6. Add ListenBrainz as a second open signal after the static ingest is stable. Version the co listen graph and apply thresholds that prevent disclosure of rare individual listening patterns.
7. Give the user a visible research lane. Candidate experiments are Word2Vec style cooccurrence and a hyperbolic embedding rebuilt from approved data. Record the hypothesis, feature set, seed, train and test split, metrics, and result artifact. Do not make either model a required server dependency.
8. Keep audio out of the first release. If the user later chooses an audio experiment, use AcousticBrainz or license filtered FMA features. Keep it in a separate optional pipeline and never fetch or store copyrighted audio merely to reproduce Every Noise.

## Acceptance tests for imported data

An ingest should fail closed when the source license is unknown, the snapshot date is absent, the content hash is absent, or a required field changes shape. It should also report duplicate identifiers, alias collisions, unsupported relationship types, orphan edges, coordinate bounds, and the proportion of records with no genre evidence.

For similarity and layout, retain a small CC0 golden fixture. Test score symmetry where the metric promises it, zero overlap, stable tie ordering, disconnected graph components, deterministic coordinates, multilingual aliases, and artists with several distant genres. Track coverage and neighborhood stability between snapshots. Do not use the old Every Noise neighbors as the only ground truth because the underlying method and inputs are not public.

The same typed records and versioned exports can feed later model experiments without adding a second production language.
